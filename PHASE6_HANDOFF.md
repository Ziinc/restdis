## What's done

- **Item 3 — per-tenant limits.** `max_shapes`, `max_log_bytes`, `max_waiting_clients` are configurable per tenant and enforced at subscribe/append/await time via `RestdisElectric.Limits`, surfaced as `429` with an actionable message. Complete, with one narrow, documented gap: on the SSE transport, a limit hit *after* the `200` status and headers are already streamed can only end the stream, not change the status code (see the comment at the SSE branch in `apps/restdis_server/lib/restdis_server/http/electric.ex`). This is inherent to SSE, not a bug to fix.
- **Item 4 — Grafana dashboard.** Extended (not replaced) `grafana/restdis-dashboard.json` with a new "Electric shapes" row. Two panels are real and wired to actual metrics (append latency, requests-served-per-append/fan-out efficiency). Three panels are explicitly marked "(metric not yet emitted)" or "PENDING" in their title/description and reference metrics that don't exist yet — see "Remaining work" below.
- **Item 6 — migration guide and compatibility tables.** `ELECTRIC_MIGRATION.md` at repo root: a migration guide, a compatibility table verified directly against the `RestdisElectric.Eval`/`Definition`/`SqlParser` source (not the PRD's aspirational list), and a table mapping Electric's operational settings to Restdis's. It honestly documents two real gaps found while writing it — see "Remaining work."
- **Item 7 — CI conformance suite.** `test/conformance/` is a real harness using the pinned `@electric-sql/client` npm package against a running Restdis instance backed by real Postgres, wired into `.github/workflows/conformance.yml` (blocks the build on failure). This is now genuinely green: I ran it by hand end-to-end (seed → migrate → boot Restdis → run the real client) and it passes, both the initial snapshot and a live update. Building and debugging this harness caught and fixed three real bugs along the way (see commits `64c8706` and `773a98f`):
  1. The CI job's `mix ecto.create/migrate` ran from the wrong working directory and silently migrated nothing.
  2. `seed.sql` was missing a `tenant_table_config` row, without which a live Postgres write never reaches a shape at all.
  3. `RestdisBuster.Worker` never cast pgoutput's decoded row values (a live-updated integer column arrived as the string `"3"` instead of `3`), and separately `RestdisServer.HTTP.Electric` never sent the `electric-cursor` response header the real client library requires on `live=true` responses (its absence makes the client silently discard the response without ever invoking your subscription callback).
- **Item 1 — parser/validation slice of `field IN (subquery)`.** The Rustler SQL parser (`apps/restdis_electric/native/restdis_electric_sql/src/lib.rs`) and `RestdisElectric.Definition`/`Eval` accept exactly the PRD's narrow subquery shape (single-column, non-correlated, single-table, no joins/nesting/nested aggregates) and reject everything else with an actionable `400` naming the specific violated constraint. This is real, tested, and safe to build on. **It is not feature-complete** — see below.

## Remaining work, in priority order

### 1. Finish item 1: incremental live tracking for `field IN (subquery)`

This is the PRD's headline Phase 6 feature and the largest remaining piece. Today `RestdisElectric.Definition.check_subqueries/3` accepts a well-formed subquery clause structurally, then unconditionally rejects it with `{:unsupported_where, "... not supported yet: Electric does not incrementally track the subquery's live result set"}` (see `not_yet_implemented/0` in `definition.ex`). No shape can use this feature yet. The PRD's done-when criterion — "archiving a parent row removes its children from a subquery-filtered shape incrementally, with no `409`" — is not met.

What's needed, read in this order before writing code:
- `apps/restdis_electric/lib/restdis_electric/eval.ex` — `subqueries/1` already extracts every `{table, column, selection}` subquery clause from a parsed filter tree; `evaluate/2` currently treats the node as `:null` (never matches) since it can't be decided from one row. This is documented in the moduledoc as something that must never reach production evaluation — i.e., don't just delete the `not_yet_implemented()` rejection without building the tracking machinery, or you'll silently serve wrong shapes.
- `apps/restdis_electric/lib/restdis_electric/filter.ex` — the Phase 3 `(table, column, constant)` hash index for the *outer* table's own filter clauses. A subquery clause needs new, separate tracking keyed on the *inner* (subquery's) table: when a row changes there, you need to know which outer rows might have flipped membership.
- `apps/restdis_electric/lib/restdis_electric/wal.ex` and `shape_registry.ex` — how a shape currently subscribes only to its own table's WAL changes. A shape with a subquery clause must *also* subscribe to the inner table's changes.
- `apps/restdis_electric/lib/restdis_electric/snapshotter.ex` and `snapshotter/postgrest.ex`/`direct_postgres.ex` — the snapshot path already round-trips through Postgres/PostgREST for the initial read; the simplest correct approach for the *snapshot* half of this feature is likely to delegate the whole `WHERE` clause including the subquery to Postgres directly (it already evaluates arbitrary SQL), rather than reimplementing subquery evaluation client-side for a one-time read. The genuinely new work is only the *live* half: incremental tracking on the inner table's changes.

Concretely:
1. New module (e.g. `RestdisElectric.SubqueryTracker`): given a shape's subquery clause (inner table + inner filter + inner column, already parsed and validated), maintains or recomputes the current set of matching inner ids, and on a WAL change to the inner table, decides whether that change added/removed an id from the matching set.
2. When the matching set changes for some id, find every outer-shape row whose `field` equals that id — either via a reverse lookup you build, or (simpler, and probably the right first cut given the PRD's own admission that a hash hit rate is not required for correctness) by querying the outer table directly for `field = <id>` through the existing origin/snapshot machinery, then emitting `insert`/`delete` messages accordingly.
3. Wire `RestdisElectric.WAL`/`ShapeRegistry` so a shape with a subquery clause also routes inner-table changes to this tracker.
4. Only then, remove the unconditional rejection in `Definition.check_subqueries/3` for this validated shape.
5. Integration test against real Postgres reproducing the PRD's own example: `parents(id, archived boolean)` and `children(id, parent_id)`, a shape on `children` filtered by `parent_id IN (SELECT id FROM parents WHERE archived = false)`; archiving a parent produces `delete` messages for its children, no `409`.
6. Reject-path tests already exist (`eval_test.exs`, `definition_test.exs`) for correlated/joined/nested/multi-column subqueries — extend, don't duplicate.

Two prior attempts at this in the same session judged it too large to land safely in one sitting and explicitly declined to fake partial coverage — treat it as its own multi-session piece of work, not a quick follow-up.

### 2. Item 5: log retention / truncation to a configured length

Not started at all. The PRD requires: "Truncate each log to its configured length, per shape with a tenant default. Return `409` to any client that resumes below the retained window." Today `RestdisElectric.Limits`/`Log` only enforce a hard *byte budget* that rejects new appends outright (Phase 6 item 3) — that is a different mechanism from what item 5 asks for, which is a rolling window that evicts the *old* tail as new operations arrive, keeping recent history bounded while never rejecting a write. Read `RestdisElectric.Log`'s chunk/index model (Phase 1) before starting; the truncation needs to delete whole closed chunks from the front of the log once the shape's configured retention count is exceeded, and the existing "resume below the retained window → `409`" path already exists conceptually for other invalidation causes (reuse it, don't build a second one).

### 3. Gatekeeper mode and the `secret` query parameter (Phase 2 scope, not Phase 6, but a real gap `ELECTRIC_MIGRATION.md` already flags)

Not Phase 6 work, but worth flagging because it's a correctness/security gap discovered while writing the migration docs: there is no gatekeeper mode (`queryable_columns` allow-list, tenant-named shape definitions) anywhere in the code — every tenant is effectively "open mode" today, which the PRD calls out as the *unsafe* default to ship. Separately, the `secret` query parameter is neither read nor rejected; it's silently ignored, which violates the PRD's own rule that "every unsupported entry is a `400`." Whoever owns Phase 2 follow-up should pick this up; it's out of scope for whoever continues Phase 6, but don't be surprised if it's flagged in review.

### 4. Finish the three pending Grafana panels (item 4, small)

Three panels in `grafana/restdis-dashboard.json` (ids 23, 24, 26 — "active shapes per tenant", "delay from write to client", "log disk use per tenant") reference metrics that don't exist. Each panel's `description` field already states exactly what telemetry event and tags it expects. This is a small, mechanical task once the emitting code exists: emit the telemetry event at the right call site, then delete "(metric not yet emitted)" from the panel title. The 409-by-cause panel (id 25) is closer: it just needs a `cause` tag added to the existing 409 telemetry in `RestdisServer.HTTP.Electric`, tagging with values like `handle_mismatch`, `schema_drift`, `shape_limit_exceeded` per the PRD's "Every reason we return 409" table.

## Known environment flake (not a code bug)

`RestdisElectric.SchemaWatcherPostgresTest`'s "adding a column with no WAL notification invalidates the shape within one poll" test occasionally fails when run as part of the full umbrella suite under CPU contention (it passes reliably in isolation: `mix test test/restdis_electric/schema_watcher_postgres_test.exs`). It's a timing-sensitive test waiting on a short poll interval; this sandbox is a shared, slow VM. Confirm it's still flaky-only (not a real regression) before spending time on it, but don't block on it.

## Local dev environment notes (for whoever picks this up in a fresh sandbox)

- Elixir/Erlang/Rust are not preinstalled in a bare sandbox; this repo pins versions in `.mise.toml` (`erlang 28.5`, `elixir 1.20.3-otp-28`) — install `mise` and run `mise install`, then `eval "$(mise activate bash)"` before any `mix` command. The system `apt` Elixir (1.14) is too old to compile this repo's dependencies.
- Postgres needs `wal_level=logical` and password auth for `localhost` (the project's own `docker-compose.yml` shows the exact settings); if Docker isn't available, `apt install postgresql` and manually set `wal_level=logical` via `pg_conftool`, enable `scram-sha-256` in `pg_hba.conf`, and create `restdis_dev`/`restdis_test` databases.
- To run the real conformance harness by hand (recommended before declaring item 1 or item 5 done): seed `test/conformance/seed.sql` against a fresh `restdis_dev`, boot the app with `MIX_ENV=dev RESTDIS_SNAPSHOT_READER=direct_postgres mix run --no-halt`, then `cd test/conformance && npm ci && npm test` with `RESTDIS_URL`/`RESTDIS_API_KEY`/`CONFORMANCE_DATABASE_URL` set per `.github/workflows/conformance.yml`. This is genuinely the fastest way to catch a real client-incompatibility bug — two of the three bugs fixed in commit `773a98f` were invisible to `mix test` entirely and only showed up against the real npm package.
